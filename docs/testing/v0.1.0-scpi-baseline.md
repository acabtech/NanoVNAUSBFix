# v0.1.0 SCPI baseline

This is the command contract and transcript for the v0.1.0 unofficial firmware.
It exists so v0.2.0 changes can be diffed against a known surface instead of
reviewed from memory.

## Capture status

- Contract frozen: **yes**.
- Hardware transcript captured: **yes** on 2026-11-02, Linux 7.2.8-9-omarchy,
  firmware `NanoVNA-H,USBFix,1.2.50,00000000`.
- Transcript: [`v0.1.0-scpi-transcript.txt`](v0.1.0-scpi-transcript.txt).
- Hang evidence: [`v0.1.0-scpi-hang.txt`](v0.1.0-scpi-hang.txt).

Run the capture helper:

```bash
sudo scripts/install-udev.sh
./scripts/capture-scpi-baseline.sh usb:0x0483:0x5740 > docs/testing/v0.1.0-scpi-transcript.txt
```

The helper only sends read-only queries. It does not change sweep settings,
calibration, or saved state. The `:VNA:CMD?` escape hatch is excluded by
default because of the v0.1.0 hang described below; set `INCLUDE_ESCAPE=1` only
on a unit you can power-cycle.

## Baseline commands

These commands are part of the v0.1.0 contract and must continue to work in
v0.2.0 unless a deprecation is documented in [`../../CHANGELOG.md`](../../CHANGELOG.md).

| Command | Kind | v0.1.0 behavior |
| --- | --- | --- |
| `*IDN?` | query | `NanoVNA-H,USBFix,1.2.50,00000000` |
| `*OPC?` | query | `1` (constant in v0.1.0) |
| `*CLS` | write | Accepted, no response |
| `*RST` | write | Accepted, no VNA reset in v0.1.0 |
| `:SYST:ERR?` | query | `0,"No error"` (no error queue in v0.1.0) |
| `:VNA:SWE:START <Hz>` | write | Set sweep start |
| `:VNA:SWE:STOP <Hz>` | write | Set sweep stop |
| `:VNA:SWE:POINTS <n>` | write | Set point count, capped by `SWEEP_POINTS_MAX` |
| `:VNA:SWE:START?` | query | Integer Hz |
| `:VNA:SWE:STOP?` | query | Integer Hz |
| `:VNA:SWE:POINTS?` | query | Integer point count |
| `:VNA:SWE:EXEC` | write | Run one synchronous sweep |
| `:VNA:FREQ <Hz>` | write | Pause and tune to one frequency |
| `:VNA:FREQ?` | query | Integer Hz |
| `:VNA:PAUSE` | write | Pause continuous sweep |
| `:VNA:RESUME` | write | Resume continuous sweep |
| `:VNA:DATA? [ch]` | query | `freq,re,im` lines, first chunk that fits |
| `:VNA:DATA:CHUNK? <ch>,<start>,<count>` | query | Windowed `freq,re,im` lines |
| `:VNA:CMD <command>` | write | Run stock shell command, discard output |
| `:VNA:CMD? <command>` | query | **Broken in v0.1.0 for `info`/`version`**: the query times out and wedges later USBTMC requests until the device is power-cycled |

Channel numbers: `0` is S11, `1` is S21.

## Baseline capture findings

The hardware capture confirmed the sweep and data surface and exposed one
release-blocking v0.1.0 bug:

- `:VNA:CMD? info` and `:VNA:CMD? version` do not return. The first timeout
  leaves the USBTMC stack unresponsive; even a later `*IDN?` times out.
- The only known recovery is a power cycle or USB re-enumeration that resets
  the application.
- The default capture helper therefore excludes the escape hatch. M1 must fix
  this path and add a regression test before the escape hatch is advertised as
  reliable.

## v0.2.0 development verification

The first v0.2.0 change fixes the escape hatch:

- `patches/0003-usbtmc-shell-output.patch` routes shell output by thread and
  implements the single-byte `put` hook used by ChibiOS `chvprintf()`.
- The rebuilt unofficial image was flashed to hardware and
  `:VNA:CMD? info`, `:VNA:CMD? version` and `:VNA:CMD? smooth` all returned
  output. A subsequent `*IDN?` and data query still succeeded, so the device no
  longer wedges.
- Development transcript (including the escape hatch):
  [`v0.2.0-scpi-dev-transcript.txt`](v0.2.0-scpi-dev-transcript.txt).

## Known v0.1.0 limitations

These are the gaps v0.2.0 closes, not accidental behavior to preserve:

- No SCPI error queue; `:SYST:ERR?` is constant.
- `*OPC?` does not wait for an active sweep or calibration.
- No abort/clear recovery for a stopped USBTMC transfer.
- No binary/IEEE-488.2 block response; data is ASCII lines.
- No screenshot over USBTMC; `:VNA:CMD? capture` is unsupported because the
  screenshot path and the USBTMC response path share `spi_buffer`.
- `:VNA:CMD?` can wedge the USBTMC stack; see the capture findings above.
- No autoset, calibration session, marker, trace math, or measurement-depth
  commands beyond the sweep and data surface.
